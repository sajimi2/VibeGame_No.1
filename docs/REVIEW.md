# Codex 审查清单

## 最小 demo 验收标准（用户最新指示，优先于此前严格条目）
- 目标是尽快获得可试玩的核心闭环。ACCEPTED 表示足以进入下一阶段，不代表发布级质量或所有环境验证完毕。
- 阻塞：无法启动、崩溃、正常窗口/常规输入下明显操作错误、核心机制失效（如无限重复伤害、无法死亡重试）、不可恢复的数据损坏。
- 非阻塞：特殊缩放/失焦/DPI、多屏、极小窗口、占位画面、主观参数、非关键代码整洁度。明确记录限制，不单独卡阶段推进。
- 复审只检查本次修复和相关回归；已通过且未受影响的模块不重复深挖，不追求测试数量。
- 技术检查与主观试玩分开；用户手感未确认可以挂起，允许先继续开发。必要检查仍须真实执行，不虚报结果。
- 实现者自主完成常规参数与私有实现选择，不为低影响选择新开审批。协议更改仍记录实际影响，设计者在交接中一次性裁定。

## 每轮技术审查
读取任务报告与实际文件差异，核对约定范围和公共签名。重跑 scripts/check.ps1 及当轮业务测试。
重点检查状态机合法转换、物理步时间、信号重复连接、去重生命周期、Resource 共享修改、奖励重复和 UI 越权。
所有缺陷报告包含：严重度、文件/行号、触发步骤、影响、期望行为与修复验证。

## 试玩证据
- T01：移动、斜向、墙角、相机与缩放后瞄准。
- T02：轻重击打空、快速连按、低体力、闪避边界、正背面格挡、死亡重试。
- T03：一对一与一对三、墙后远程、脱战、连续重试。
- T04/05：满包换装、连续穿脱、跨级奖励、UI 开关不发奖。
- T06/07：完整流程、任务交付两次、重启读档、导出版本独立启动。

区分“自动验证通过”“人工操作通过”“用户手感待确认”和“未验证”。
代码审查通过不代表用户认可手感；手感问题单独记参数、复现情景和调整建议。
ACCEPTED 按上述 demo 标准要求核心功能和相关检查通过；未完成的图形/硬件/体验验证须明确列出，但非阻塞项允许延后。
